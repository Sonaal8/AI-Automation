01

The marketing problem

CRM teams frequently need an audience extracted from a data platform so a campaign can be launched. When every request requires manual analyst handling, turnaround and analyst capacity become bottlenecks.

◷ Before: manual request handling

  • Marketing submits audience criteria on a request board.
  • An analyst interprets the request and opens the data platform.
  • The analyst writes or adapts SQL and checks exclusion criteria.
  • The output file is saved to a repository.
  • The analyst returns to the board to attach/comment and update status.

✦ After: AI-assisted workflow

  • Read and normalize the incoming request.
  • Compare the request against historical examples.
  • Reuse approved logic when the match is strong; otherwise draft a query for review.
  • Run validation checks and create a safe preview.
  • Prepare the output and board update while keeping a human approval gate.
Design principle: automate repeatable work, not accountability. The workflow can assist with matching, query drafting and orchestration, but audience logic and exclusions must still be verified before production delivery.

03

Decision logic: reuse or draft?

The most important decision is whether a request is sufficiently similar to a previously approved pattern. A partial match should not be treated as permission to auto-run a query.

High-confidence match

Key criteria match an approved historical example. Reuse its query template, bind the current values, and still require output review.

Reuse approved logicReview output
→

Controlled processing

Run static checks, preview audience counts, inspect exclusions, and prepare the request-board update only after checks pass.

No safe match

The request differs on an important attribute, or the repository does not contain a sufficiently similar approved pattern.

Draft onlyNo blind execution
→

Review queue

Draft a query for analyst review. The reviewer confirms business definitions, exclusions, table/column logic and expected audience size.

Why this matters: an LLM can generate plausible SQL that is still wrong. Historical matching, static checks, warehouse permissions and human review are separate layers—not substitutes for one another.

05

Quality controls and human oversight

The objective is to reduce repetitive work while preserving data quality, privacy and accountability.

🛡️ Automated checks

  • Required request fields and value ranges.
  • Historical template match score and reason.
  • SQL draft checks: SELECT-only shape, one statement and LIMIT requirement.
  • Preview count and sample records using local demo data.
  • Audit event and request status payload.

👤 Human reviewer confirms

  • Business interpretation of the audience definition.
  • Correct inclusion and exclusion criteria.
  • Expected audience size and sample rows.
  • Permitted data sources and query performance.
  • Approval before any campaign delivery or live board update.
Demo limitation: this project uses local sample data. It does not call a real LLM, access Monday.com, or execute SQL in Databricks. The workflow illustrates the architecture and review controls; live integrations require separate credentials, permissions, testing and approval.

Business impact: what to measure

Use operational metrics to demonstrate whether automation actually creates capacity and improves service levels.

85–90%Initial testing accuracy reported in the project context. Validate against a labelled test set before making a performance claim.
TurnaroundMedian time from request submission to review-ready output, segmented by request type.
Analyst effortActive minutes spent per request before and after automation—not just elapsed time.
QualityFirst-pass approval rate, rework rate, exclusion errors and production incidents.
Example calculation: if median turnaround falls from 60 minutes to 15 minutes, elapsed turnaround is reduced by 75%. Measure analyst active time separately before claiming a 75% reduction in effort.
